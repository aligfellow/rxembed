# Can the donor-fold tables be group/period-scaled instead of per-(element, hyb)?

READ-ONLY investigation. The maintainer finds `_FOLD_WINDOW` / `_FOLD_MEDIAN` (10 dedicated
`(element, hyb)` rows) "a little specific" and would rather scale by periodic group/period, and notes
it is "unclear why or where these are from." This documents the origin and tests the scaling honestly.

Tables live in `src/rxembed/rdkit_embed/constraints/donor_orient.py:44-67`; read by BOTH the
enforcement side (`_orient_donor`, `_ORIENT_WALL` = `_FOLD_WALL_FLOOR`) and the gate/metric side
(`coordination.donor_orientation` / `donor_fold`) — one ruler, two consumers, so they cannot drift.

## 1. ORIGIN (this alone answers "unclear where from")

**A measured crystallographic census, not a guess.** The numbers were produced by a streaming M→D→X
angle census over a transition-metal-complex crystal corpus:

- **Generator:** `tools/donor_angle_census.py` in the sibling **OIN-SMILES** repo (commit `a05f2bc6`,
  "donor-fold walk + M-D-X angle census"). Recovered in full for this investigation. It walks every
  metal→donor→heavy-substituent triple, strips the metal first (so the dative bond does not mis-type
  the donor's hybridisation), buckets angles by `(donor element, hybridisation)`, and prints
  percentiles `p0.5, p5, p50, p95, p99.5` per bucket.
- **Corpus:** `tests/fixtures/*.xyz` + `tests/integration/tmQM/*.xyz` — the **tmQM (Kulik) transition-
  metal-complex crystal set** plus curated fixtures. In rxembed this became **721 M-D-X angles across
  121 crystal structures, 10 classes** (borane/carborane cages excluded — UFF has no B_5/B_6 types;
  see `playground/corpus_regression/cr_corpus.py`).
- **How each number is derived** (per the generator + the docstrings at
  `donor_orient.py:34-42`, `coordination.py:198`):
  - **floor** = `min(p0.5, corpus_min) − 5°`  → calibrated to **0 false flags on 144 held-out crystals**.
  - **ceiling** = `p99.5 + 5°`  (capped at the physical 180°).
  - **median** = `p50`  → reference-free: `fold = max|M-D-X − median|` needs no comparison structure.
  - a class with **n < 6 abstains** (never gated) — a threshold read off < 6 donations is noise.
    (OIN used the stricter `n ≥ 20`, which is why OIN has 8 classes and rxembed 10: relaxing to n ≥ 6
    admits `(As, sp3)` and `(N, sp)`.)
- **This is DATA by the project's own policy.** `AGENTS.md:34-35`: *"Where a genuine physical constant
  must be tabulated (covalent radii, census fold windows), that is data — tabulate it and say where the
  numbers came from."* The fold windows are named there as the canonical example.

So: **origin = a percentile summary of 721 real M-D-X donation angles from tmQM/Kulik crystals**,
generated by `OIN-SMILES tools/donor_angle_census.py`. The provenance is presently only in prose
docstrings; the concrete *generator path + corpus + percentile rule* is what is missing from the table
itself, and is the cheapest fix (recommendation b).

## 2. GENERALISABILITY — fit a group/period model, per-row residuals

Two distinct quantities are tabulated and they behave oppositely.

### The MEDIAN is smooth — group/period/hyb reproduces it

The median is essentially the donor's **VSEPR ideal angle for its hybridisation**, plus a few-degree
offset:

- bare `ideal(hyb)` (sp 180 / sp2 120 / sp3 109.5), **zero fitted params**: RMSE **5.1°**, max |res| 9.9°.
- `median = ideal(hyb) + 2.16 + 3.11·(period−2) − 1.44·(group−14)`, 3 params: RMSE **4.2°**, max 8.5°.

Per-row residual (fitted model):

| class     | median | model | resid |
|-----------|-------:|------:|------:|
| (N, sp2)  | 120.7  | 120.7 |  −0.0 |
| (P, sp3)  | 115.8  | 113.3 |  +2.5 |
| (C, sp2)  | 124.4  | 122.2 |  +2.2 |
| (N, sp3)  | 110.3  | 110.2 |  +0.1 |
| (C, sp)   | 176.2  | 182.2 |  −6.0 |
| (O, sp2)  | 125.7  | 119.3 |  +6.4 |
| (S, sp3)  | 103.4  | 111.9 |  **−8.5** |
| (C, sp3)  | 113.3  | 111.6 |  +1.7 |
| (N, sp)   | 179.3  | 180.7 |  −1.4 |
| (As, sp3) | 119.4  | 116.4 |  +3.0 |

The two axes the task flagged both show up cleanly in the median:
- **Hybridisation dominates:** sp C 176 vs sp3 C 113 — a 63° gap the `ideal(hyb)` term captures exactly.
- **Period matters, within a group:** group-15 sp3 median rises monotonically **N 110.3 → P 115.8 →
  As 119.4** (~+4.5°/period) — the `+3.11·(period−2)` term.
- **The one median outlier a smooth scale misses is `(S, sp3)` (−8.5°):** S at 103.4° is 12° below its
  same-period group-15 neighbour P at 115.8°; a linear `group` term only predicts −1.4° of that. The
  extra lone pair on a group-16 sp3 donor crowds the angle more than linear-in-group allows.

### The FLOOR (the GATE) is NOT smooth — this is where scaling fails

The floor is a **distribution tail (p0.5)**, so it encodes each class's empirical *scatter*, which is
not a periodic function. Fitting the same form to the floor:

`floor = ideal(hyb) − 23.82 + 7.57·(period−2) − 3.60·(group−14)` — RMSE **8.2°**, max |res| **18.4°**:

| class     | floor | model | resid |
|-----------|------:|------:|------:|
| (N, sp2)  |  96.0 |  92.6 |  +3.4 |
| (P, sp3)  |  89.0 |  89.6 |  −0.6 |
| (C, sp2)  |  85.0 |  96.2 | −11.2 |
| (N, sp3)  |  82.0 |  82.0 |  −0.0 |
| (C, sp)   | 155.0 | 156.2 |  −1.2 |
| (O, sp2)  |  90.0 |  89.0 |  +1.0 |
| (S, sp3)  |  91.0 |  86.0 |  +5.0 |
| (C, sp3)  | 104.0 |  85.6 |  **+18.4** |
| (N, sp)   | 140.0 | 152.6 |  **−12.6** |
| (As, sp3) |  95.0 |  97.2 |  −2.2 |

Why it can't be smooth: the floor's distance below the median (the class scatter) ranges from **−9.3°**
(`C, sp3`, a tight distribution) to **−39.4°** (`C, sp2`, a wide one) — a 4× spread that is a property
of each donor's chemistry, not of its group/period coordinates. The **sp2 and sp3 floors overlap
heavily** (sp2: 85–96; sp3: 82–104), so hybridisation — which cleanly separates the medians — does
*not* separate the floors. The ceiling and window width (25°–84°, several capped at the physical 180°)
are equally non-smooth.

## 3. RISK — is a "cleaner model" a regression here?

**Yes, on the gate half.** Two of the floor residuals are the exact failure mode the project has
already reverted twice (`metal-ff-cancellation`, `covalent-radius-tmqm-grounding`: a global-fit win
hiding a domain-fatal per-row regression):

- **`(N, sp)` floor: model 152.6° vs measured 140° → +12.6° too HIGH.** The gate rejects `angle <
  floor`. A floor raised to ~153° would **false-flag real nitrile/isocyanide crystals** that donate at
  140–152° — breaking the census's 0/144 clean-flag calibration. This is the domain-fatal direction.
- **`(C, sp3)` floor: model 85.6° vs measured 104° → −18.4° too LOW.** The gate becomes ~18° weaker on
  sp3 carbanions — a real fold to ~90° now passes silently.

The floor is the load-bearing, safety-critical number (it *gates*, and it seeds the wall via
`_FOLD_WALL_FLOOR`). A model that reproduces the median beautifully but moves a floor by 12–18° is
"cleaner but less faithful" **exactly where fidelity is required**. An 8° RMSE on a quantity whose job
is a ≤5° calibration margin (`p0.5 − 5`) is not within the census's own scatter.

---

## RECOMMENDATION

**Primary: (b) keep the measured table, add the origin reference + a why-per-class comment.** The
window/floor is a measured distribution tail that is provably non-smooth (max floor residual 18.4°;
false-flags `(N, sp)` if scaled), and it is the load-bearing gate. Per `AGENTS.md:34-35` this is *data*
and the correct fix is not to derive it but to **say where it came from** — which is currently only
implied. Concretely, add to the table's docstring:

> Generated by `OIN-SMILES tools/donor_angle_census.py` (commit `a05f2bc6`): the p0.5/p50/p99.5
> percentiles of 721 M-D-X angles over 121 tmQM(Kulik)+fixture crystals, bucketed by (element, hyb),
> metal stripped before typing. floor = min(p0.5, corpus_min) − 5° (0/144 false flags); ceiling =
> p99.5 + 5°; median = p50; n < 6 abstains. **Per-class, not group/period-scaled, because the MEDIAN is
> smooth in hybridisation (≈ VSEPR ideal ±5°) but the FLOOR is a per-class scatter tail that is not:
> a group/period fit moves the (N,sp) floor +12.6° (false-flags real nitriles) and the (C,sp3) floor
> −18.4°.** The `(S,sp3)` median is a further non-smooth point (group-16 crowding, −8.5° vs a linear
> group term).

**Acceptable partial: (c) hybrid — derive the MEDIAN, keep the measured WINDOW.** If shrinking the
table is a real goal, `_FOLD_MEDIAN` *could* be replaced by `ideal(hyb) + small offset` (RMSE 4–5°,
within its use as a `fold`-deviation reference) — but keep `(S, sp3)` as an explicit override and
**leave `_FOLD_WINDOW` measured**. This removes ~half the rows at no fidelity cost to the gate. Net
value is modest (the median half is not the safety-critical half) and it adds a second code path, so
(b) is preferred unless row-count reduction is itself the objective.

**Reject: (a) fully group/period-scaled.** Faithful for the median, a regression for the gate. Do not
replace the measured floor with a smooth model.

### Fidelity trade-off, one line
The median is VSEPR-smooth and scalable; the gate floor is a measured per-class scatter tail that is
not — scaling it re-introduces the "global fit hides a per-row regression" failure the project reverted
twice, and would false-flag real nitrile crystals.
